## Fase 1 — Item No. 7: Reporting Terintegrasi

6. Mengkonfirmasi Elasticsearch aktif dan terindeks dengan benar sebagai prasyarat Report Profiles — ditemukan 1.19 juta tiket ter-index, cluster health berstatus yellow (wajar untuk cluster single-node).
7. Membuat dan mengatur Report Profiles untuk metrik yang dibutuhkan: metrik First Response Time (median, dengan filter integritas data) ditambah 62 Report Profile (3 Category, 34 Group, 19 Organization), sudah live di staging.
8. Mengevaluasi dan memilih BI eksternal untuk kebutuhan historis di atas 6.000 baris (batas UI native Zammad) — **Grafana** dipilih dibanding Kibana. Container `grafana` ditambahkan ke `docker-compose.yml`, dibuatkan role Postgres read-only `grafana_ro`, data source "Zammad Postgres" disambungkan, dan starter dashboard "SISKA - Ticket & CSAT Overview" sudah dibuat.
9. **Keputusan pivot desain**: fitur Feedback Rating/CSAT dibangun **native di Zammad**, bukan integrasi/ETL dari sistem eksternal seperti rencana awal. Dibangun lengkap: Custom Object Attributes, Scheduler `Service::Csat::PrepareFeedbackSurveys`, `FeedbackController` publik, Trigger email, pengiriman multi-channel (Email/Telegram/WhatsApp di balik safety-toggle `csat_whatsapp_enabled`), dan Report adapter `Report::TicketCsatScore`. Detail lengkap ada di `docs/DESIGN_FEEDBACK_RATING.md`.
10. **Menemukan dan memperbaiki bug nyata** pada alur CSAT: link rating yang dikirim lewat Email/Telegram/WhatsApp awalnya tidak menyertakan parameter `&score=`, sehingga link yang diterima customer **selalu gagal** (langsung menampilkan halaman "link tidak valid"). Diperbaiki dengan mendesain ulang halaman feedback menjadi satu halaman interaktif: bintang rating satu baris (klik langsung tanpa reload halaman, murni CSS tanpa JavaScript) + kolom komentar (`csat_comment`, custom object attribute baru) + satu tombol kirim — menggantikan rancangan sebelumnya yang sempat berupa 5 link terpisah maupun alur 3 langkah (pilih→konfirmasi→submit). Sudah diuji end-to-end secara aman: email asli berhasil terkirim ke alamat test (`jajat.sudrajat@pkp.co.id`) dan submit rating berhasil menyimpan skor + komentar ke database.
11. Menyamakan styling halaman feedback dengan tampilan form native Zammad — warna, ukuran label, dan tombol diambil langsung dari `app/assets/stylesheets/zammad.scss` (bukan tebakan), ditambah logo SISKA (diambil dari Setting `product_logo` via endpoint publik `/api/v1/system_assets/`) dan kutipan (blockquote) bergaya native yang mengingatkan customer isi keluhan asli tiket mereka.

## Fase 2 — Item No. 8: Dashboard KPI Tim

12. **Keputusan pendekatan**: dashboard dibangun native ke Zammad sendiri yang memanggil API Zammad langsung (bukan embed Grafana/iframe) — diwujudkan sebagai tab baru "KPI Tim" di Dashboard **frontend legacy** (CoffeeScript/jQuery), karena itu yang aktif dipakai agent sekarang, bukan Vue `/desktop` yang halaman Dashboard-nya masih di-gate dev-only oleh tim Zammad.
13. Menetapkan daftar KPI final: First Response Time (median, rolling window), CSAT (rata-rata, rolling window), Tiket New & Open (snapshot realtime), Tiket Escalated (jumlah + rasio, realtime).
14. Membangun backend `Service::Dashboard::TeamKpi` + `TeamKpiController`, dengan filter periode rolling dari 7 hari sampai 2 tahun ke belakang.
15. Membangun frontend tab "KPI Tim" dengan styling native-style memakai SCSS asli (via `dartsass-rails`) — sudut kotak (bukan rounded), ikon berukuran sesuai native, grid 3 kartu per baris, dan warna ikon/angka yang **berbasis status** (supergood/good/ok/bad/superbad, mengikuti konvensi native Zammad sendiri) alih-alih warna tetap per kategori.
16. Deploy dan smoke test di staging (HTTP 200, precompile bersih, tanpa error di log), lalu commit dan push ke branch `feature/08-team-kpi-dashboard`, dan akhirnya di-**merge ke `main`**.
17. Mendokumentasikan dan memverifikasi endpoint API `GET /api/v1/team_kpi?days=N` bisa dipanggil dari aplikasi lain di luar Zammad — dibuatkan akun service khusus `integration-kpi-api@pkp.co.id` (role "Customer Services", tidak terikat ke satu orang) beserta Personal Access Token (permission `ticket.agent`), lalu diuji nyata lewat `curl` dari luar (berhasil, termasuk verifikasi field escalated konsisten di semua rentang `days`). Kontrak API (route, cara autentikasi, skema response lengkap) didokumentasikan di `docs/DESIGN_TEAM_KPI_DASHBOARD.md` Section 7.
18. Menambahkan auto-refresh berkala untuk tab "KPI Tim" — Setting baru `team_kpi_auto_refresh_seconds` (default 300 detik/5 menit, `0` untuk mematikan). Dipilih polling sederhana (bukan WebSocket/push) karena metriknya tidak butuh update sub-detik. Timer tetap jalan di background, tapi request AJAX cuma benar-benar dikirim kalau tab browser aktif DAN sub-tab "KPI Tim" sedang dipilih — supaya tidak boros query database saat tidak ada yang melihat. Refresh-nya silent (tanpa indikator loading, tetap tampilkan data terakhir kalau gagal). Sudah di-deploy dan diverifikasi di staging.
19. **Menemukan dan mendokumentasikan gap nyata**: semua Setting custom yang dibuat di project ini (CSAT: `csat_feedback_expiry_days`, `csat_whatsapp_enabled`, dll; KPI Tim: `team_kpi_auto_refresh_seconds`) ternyata **tidak bisa ditemukan lewat Admin > Settings** di Zammad — diverifikasi langsung ke kode frontend, layar itu hard-coded hanya untuk area bawaan (System/Security/Ticket/Branding), tidak ada pencarian lintas-area, dan area custom (`CSAT::Base`/`TeamKpi::Base`) tidak terdaftar di tab manapun.
20. **Membangun tab Admin UI baru "SISKA"** (`app/assets/javascripts/app/controllers/_manage/siska_settings.coffee`) untuk menutup gap di atas — dua sub-tab ("CSAT", "KPI Tim") memakai mekanisme generik `App.SettingsArea` yang persis sama dengan yang dipakai tab System/Branding bawaan Zammad, jadi semua 6 Setting sekarang bisa dilihat dan diubah lewat Admin UI biasa, tidak perlu lagi Rails console/API.
21. **Menemukan dan memperbaiki bug permission**: sambil membangun tab di atas, ditemukan bahwa keenam Setting itu memakai permission `admin.setting_system` yang **tidak pernah ada** sebagai Permission asli di Zammad (`Permission.where(name: 'admin.setting_system').exists?` → `false`) — kalaupun ada UI yang mencoba menampilkannya, tidak ada satupun user, termasuk admin, yang akan lolos pengecekan. Diperbaiki ke `admin.system` (permission asli yang juga dipakai tab "System" bawaan) di database live maupun di ketiga source script (`create_csat_object_attributes.rb`, `create_csat_message_settings.rb`, `create_team_kpi_settings.rb`). Kedua design doc diperbarui untuk mencerminkan cara yang benar (Admin UI, Rails console, atau API) sekaligus mencatat riwayat dua bug ini.
22. **Menemukan dan memperbaiki bug ketiga**: begitu tab "SISKA" dicek langsung di browser, sub-tab "CSAT" ternyata blank/error total — console menunjukkan `Uncaught No such options.form for csat_feature_launched_at`. Setting itu dibuat dengan `options: {}` kosong (dianggap "internal-only", tidak pernah dipikirkan akan tampil di UI generik), padahal renderer Admin Zammad (`App.SettingsArea`) mewajibkan setiap Setting di suatu area punya `options.form` untuk bisa dirender, dan langsung crash kalau tidak ada. Diperbaiki dengan menambahkan form definition (input text sederhana) di database live dan di source script. Diverifikasi ulang langsung oleh user di browser: tab CSAT sekarang tampil lengkap dengan semua field beserta tombol Submit masing-masing.
23. **Mengubah semua nilai kalibrasi yang sebelumnya hardcoded jadi Setting** — threshold warna FRT (60/240/480/1440 menit), CSAT (4.5/4.0/3.0/2.0), dan Escalated (20/40/65/90%) di `team_kpi.rb`, ditambah `team_kpi_default_window_days` (7) dan `team_kpi_max_window_days` (730), sekarang jadi 5 Setting baru yang bisa diatur lewat tab "SISKA > KPI Tim" tanpa redeploy. Frontend (`team_kpi.coffee`) juga diubah membaca default window dari Setting yang sama (lewat `App.Config`), menggantikan konstanta `DEFAULT_RANGE` yang sebelumnya terpisah dan berisiko beda nilai dengan backend — label "(default)" yang di-hardcode di dropdown juga dihapus karena defaultnya sekarang dinamis. Diverifikasi lewat API: hasil threshold/state identik dengan sebelum refactor untuk data yang sama, jadi ini murni membuat nilai yang sudah ada configurable, bukan mengubah perilaku.
24. **Mulai riset Fase 3 (Item No. 3 & 12 — Status Eskalasi + Update Alur Status Tiket)**, sebelum implementasi apapun. Temuan penting: gap analysis awal mengkategorikan seluruh item ini sebagai "custom dev wajib", padahal riset lanjutan menemukan **sebagian besar requirement item No. 12 (validasi urutan transisi status Open→In Progress→Eskalasi→Closed, termasuk pembatasan per role) sebenarnya sudah native lewat fitur Core Workflow Zammad** — ditegakkan di server (bukan cuma tampilan), bisa dikonfigurasi lewat Admin UI tanpa kode sama sekali. Kemungkinan ini yang tidak diketahui saat requirement awal diajukan. Yang genuinely tetap butuh custom dev cuma bagian "SLA dihitung ulang sejak eskalasi" (field `escalation_started_at` + Trigger — keduanya ternyata juga cukup konfigurasi — + Scheduler/service kalkulasi sisa waktu yang wajib pakai kalender jam kerja yang sama dengan SLA, bukan pengurangan waktu polos). Ditulis lengkap di dokumen desain baru `docs/DESIGN_ESCALATION_STATUS.md`, termasuk 2 keputusan yang sudah disepakati: SLA native dibiarkan tetap jalan paralel (tidak dibekukan, via checkbox `ignore_escalation` yang dibiarkan default off), dan transisi status belum dibatasi role (bisa ditambahkan admin sendiri kapan saja lewat Core Workflow tanpa kode). Beberapa keputusan bisnis masih terbuka (budget waktu breach, lokasi tampilan sisa waktu) sebelum lanjut implementasi.

## Fase 3 — Item No. 3 & 12: Status Eskalasi + Update Alur Status Tiket (lanjutan)

25. **Mengimplementasikan bagian native/config dari alur status Eskalasi** yang sudah diriset sebelumnya: state baru "In Progress" dan "Eskalasi" (kategori `open`), Custom Object Attribute `escalation_started_at` (Ticket) serta `escalation_budget_hours` (Group & Organization, untuk override budget waktu per tim/customer — Group menang kalau keduanya di-set), Setting global `escalation_budget_hours` (default 8 jam kerja, muncul di tab "SISKA > Eskalasi" yang baru ditambahkan), Trigger otomatis yang mengisi `escalation_started_at` saat tiket masuk status Eskalasi, dan aturan Core Workflow yang mencegah tiket lompat langsung dari Open ke Eskalasi (harus lewat In Progress dulu) sambil tetap membolehkan Closed dari state manapun.
26. **Menemukan dan memperbaiki 2 bug tersembunyi** saat membangun aturan Core Workflow — keduanya gagal **tanpa menampilkan error sama sekali**, sehingga baru ketahuan setelah reproduksi manual langkah-demi-langkah: (1) format JSON `perform` butuh key `'operator'` eksplisit menyebutkan nama aksinya, bukan langsung memakai nama aksi sebagai key; (2) nilai ID state harus disimpan sebagai string, bukan integer, karena mekanisme pembanding opsi Core Workflow tidak melakukan type coercion antara angka dan teks. Juga ditemukan bahwa Core Workflow **tidak aktif sama sekali** kalau tiket diubah lewat `ticket.update!` langsung di Rails console — validasinya cuma jalan lewat controller/API asli (butuh atribut `screen` yang di-set otomatis oleh `TicketsController#update`), sehingga pengujian yang benar wajib lewat API HTTP sungguhan, bukan skrip Ruby biasa (skrip Ruby biasa akan tampak "berhasil" padahal validasinya sebenarnya tidak pernah berjalan).
27. **Memverifikasi seluruh alur end-to-end lewat API sungguhan** (bukan Rails console, sesuai pelajaran di atas): mencoba pindah status langsung dari Open ke Eskalasi berhasil diblokir (HTTP 422 dengan pesan error yang jelas), alur yang sah (Open → In Progress → Eskalasi) berhasil, dan `escalation_started_at` otomatis terisi oleh Trigger begitu tiket masuk status Eskalasi. Bagian yang masih tersisa: keputusan lokasi tampilan sisa waktu (widget tiket / kolom Overview / card KPI Tim), baru setelah itu Scheduler/service kalkulasi sisa waktu bisa dibangun.
