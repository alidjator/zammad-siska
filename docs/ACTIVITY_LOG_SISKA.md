## Di Luar Fase — Tindak Lanjut Bug Timezone ~7 Jam

28. **Root cause bug timezone ~7 jam (`first_response_at`/`close_at`/`last_contact_at`) dikonfirmasi dengan bukti konkret (tahap awal).** User melakukan survey langsung ke server database production asli (tempat Zammad 3.4.0 lama berjalan) dan menemukan: timezone sistem server = **WIB (UTC+7)**, dan MySQL dikonfigurasi `time_zone = SYSTEM` — artinya `NOW()` di level SQL server itu selalu mengembalikan waktu lokal WIB, bukan UTC. Status hipotesis naik dari "kemungkinan besar" menjadi "didukung bukti konkret".
29. **Root cause DIKONFIRMASI SEPENUHNYA** lewat investigasi lanjutan langsung ke server Zammad 3.4.0 production (akses SSH + database, semua read-only: baca source code, `rails console` cuma `puts`, query `SELECT`/`DESCRIBE`). Ditemukan penyebab pastinya: kolom `tickets.first_response_at`/`close_at`/`last_contact_at` bertipe MySQL **`TIMESTAMP`** (punya semantik timezone, otomatis dikonversi berdasar timezone sesi koneksi = WIB), sedangkan `tickets.created_at`/`ticket_articles.created_at` bertipe **`DATETIME`** (tanpa semantik timezone sama sekali) dan `preferences` tersimpan sebagai JSON (juga tanpa semantik timezone) — dua yang terakhir ini karena itu selalu benar, sementara tiga kolom `TIMESTAMP` di atas salah. Konfigurasi Rails sendiri (`ActiveRecord::Base.default_timezone = utc`, tidak ada override `Time.zone` yang bocor, tidak ada kode yang salah pakai `Time.now`) semuanya terbukti benar — jadi kesimpulan akhirnya: **ini bukan bug di kode Zammad manapun (3.4.0 maupun 7.1.3)**, melainkan efek samping proses migrasi data MySQL→PostgreSQL yang tidak menangani ulang konversi timezone otomatis yang seharusnya terjadi khusus untuk kolom bertipe `TIMESTAMP`. Karena arah dan besar pergeseran (-7 jam) sekarang diketahui pasti, koreksi data historis (kalau nanti diputuskan perlu) bisa dieksekusi dengan keyakinan tinggi. Laporan bug diperbarui lengkap dengan seluruh jejak investigasi (setiap command yang dijalankan dan hasilnya).

30. **Mengeksekusi koreksi data historis di staging** setelah root cause bug timezone dikonfirmasi sepenuhnya. Sebelum eksekusi: divalidasi dulu dengan sample 12 tiket acak (termasuk yang tidak lolos deteksi anomali lama) — 12 dari 12 menunjukkan selisih persis -7 jam terhadap referensi ground-truth, mengonfirmasi bug menggeser SEMUA tiket migrasi secara seragam, bukan cuma yang "kelihatan" anomali. Backup penuh (161.884 baris) diambil dan disimpan di luar server sebelum menulis apapun. Dry-run (`SELECT` saja, tanpa tulis) dijalankan dan hasilnya dikonfirmasi ke user sebelum eksekusi sungguhan.
    Koreksi dijalankan bertahap: `close_at` dan `last_contact_at` (`+7 jam` seragam via SQL), lalu `first_response_at` (disalin dari referensi ground-truth kalau valid, fallback `+7 jam` kalau tidak ada referensi, dan **dilewati** untuk ~67 tiket dengan referensi yang tidak konsisten — butuh tinjauan manual terpisah, bukan dikoreksi asal tebak). Hasil eksekusi **cocok persis** dengan dry-run, tidak ada penyimpangan. Verifikasi akhir: anomali turun dari puluhan ribu tiket (77-92% dari data historis) menjadi 0-63 baris tersisa (kasus edge yang sengaja dilewati). Skrip koreksi disusun ulang jadi satu file resmi (`script/fix_timezone_migration_bug.rb`) untuk dipakai ulang di production nanti kalau diputuskan perlu — belum dijalankan di production asli.

## Di Luar Fase — Anonimisasi Kontak User Non-Admin (Staging)

36. **Menganonimkan permanen kontak 72.017 user non-admin di staging**, setelah ada komplain email hasil testing "nyasar" ke customer asli. Investigasi awal menemukan database staging (`zammad-staging-zammad-app-1`) ternyata **salinan penuh data production** (72.032 user total), bukan data dummy, dan punya koneksi SMTP outbound yang hidup — jadi risiko kebocorannya nyata, bukan cuma teoretis.
    Sebelum eksekusi, beberapa hal penting ditemukan dan diklarifikasi ke user lewat pertanyaan langsung (bukan diasumsikan sendiri): (a) kolom kontak yang benar-benar ada di tabel `users` cuma `email`/`phone`/`mobile`/`fax`/`web` — WhatsApp memakai field yang sama dengan phone/mobile, sedangkan **Telegram tidak punya kolom per-user yang stabil** (kemungkinan cuma tersimpan di `ticket_articles.preferences` per pesan, scope jauh lebih besar/berisiko) — diputuskan **ditunda**, tidak diproses sekarang; (b) scope "Customer + Agent" yang awalnya disepakati literal ternyata mencakup akun `@pkp.co.id` — **termasuk akun operator proyek ini sendiri dan akun service `integration-kpi-api@pkp.co.id`** yang sudah didokumentasikan untuk integrasi eksternal — ditemukan lewat sampling data sebelum eksekusi, lalu dikonfirmasi ulang ke user dan **dikecualikan** dari scope untuk mencegah operator ter-lockout dari sistemnya sendiri.
    Eksekusi memakai **SQL mentah** (bukan lewat model `User` Rails) supaya tidak ada satu pun callback/notifikasi Zammad yang terpicu ke siapa pun, sesuai permintaan eksplisit user. Backup nilai lama (72.017 baris) diambil otomatis oleh skrip sebelum menulis apa pun — satu-satunya safety net yang tetap dipertahankan meski user memilih langsung eksekusi tanpa siklus dry-run terpisah. Logika SQL divalidasi dulu lewat transaksi yang sengaja di-rollback (tanpa menulis apa pun secara permanen) sebelum dijalankan sungguhan.
    Format baru: email/login jadi `anon-<id>-<acak>@anon.invalid` (TLD `.invalid` dijamin RFC 2606 tidak akan pernah bisa dikirimi email sungguhan, `<id>` menjamin keunikan), phone/mobile (kalau aslinya terisi) jadi `id` di-zero-pad 16 digit — sengaja dibuat bukan berpola nomor telepon, sesuai permintaan eksplisit user.
    Eksekusi tulis massal ini diblokir untuk Claude oleh auto-mode classifier (sama seperti pola koreksi bug timezone sebelumnya) — skrip yang sudah tervalidasi diserahkan ke user untuk dijalankan manual lewat `docker exec`, berhasil 72.017 baris ter-update sesuai ekspektasi persis.
    Didokumentasikan lengkap di `docs/ANONYMIZATION_CONTACT_INFO.md`, dengan contoh before/after **di-mask sebagian** (bukan PII asli utuh) — supaya dokumen yang di-commit ke git tidak menciptakan catatan permanen baru berisi PII asli, yang justru bertentangan dengan tujuan pekerjaan ini sendiri. File backup nilai asli lengkap dipindahkan ke penyimpanan permanen di host (`/usr/local/src/claudeai/backups/`, checksum diverifikasi), tidak pernah di-commit ke git.

Pencarian awal di tabel `ticket_articles` (email reply/artikel biasa) tidak menemukan bukti — tapi ini ternyata pencarian yang tidak lengkap: notifikasi "tiket diperbarui" ke anggota Group (bukan ke customer) dikirim langsung lewat `NotificationFactory::Mailer`/ActionMailer, **tidak pernah tercatat sebagai baris di `ticket_articles`**, dan levelnya `debug` di kode sumber sehingga juga tidak muncul di `production.log` (yang berjalan di level `INFO`). Baru ditemukan setelah user menunjukkan screenshot email notifikasi asli yang benar-benar diterima (ke `trianjas.saputra@sim.co.id`), memaksa pencarian ulang dengan metodologi berbeda: analisis langsung tabel `histories`, yang ternyata mencatat setiap peristiwa notifikasi (baris dengan pola `<email>(<jenis>:<kanal>)`) secara rinci dan presisi.
    Hasil investigasi penuh (5 tiket diperiksa): **121 dari 168 notifikasi tercatat** benar-benar terpicu oleh aktivitas pengujian proyek (2 tiket test buatan sendiri untuk CSAT & Eskalasi, plus 1 tiket produksi yang diubah statusnya via UI untuk verifikasi live), terkirim ke 8 alamat berbeda — 2 di antaranya individu bernama asli (`trianjas.saputra@sim.co.id`, `dita.herma@sim.co.id`), sisanya tampak alamat/inbox bersama tim. Akar penyebabnya perilaku bawaan Zammad (notifikasi otomatis ke seluruh anggota Group saat status tiket berubah, lewat `Transaction::Notification#possible_recipients_of_group` yang membaca `User.group_access(group_id, 'full')`), bukan bug pada kode yang dikembangkan proyek ini — tapi tetap berisiko nyata karena Group yang dipakai tiket test (Business Support/Customer Services) beranggotakan staf sungguhan.
    Laporan investigasi disusun sebagai laporan formal (ringkasan eksekutif, metodologi, temuan rinci, kesimpulan, rekomendasi) — **sengaja ditampilkan langsung di percakapan saja, tidak disimpan sebagai file di mana pun** (baik ke git maupun lokal), atas permintaan eksplisit user, karena memuat alamat email individu bernama asli.
38. **Mengimplementasikan mitigasi #1 dari rekomendasi laporan di atas**: Group baru `QA - Internal Testing` (id 89) dibuat khusus untuk tiket pengujian internal proyek ke depannya, sengaja dibuat **tanpa anggota** (`groups_users` kosong sejak dibuat, tidak pernah diisi). Diverifikasi langsung lewat kode sumber yang sama dipakai mekanisme notifikasi asli (`User.group_access(89, 'full')` mengembalikan 0 penerima) — bukan cuma diasumsikan aman. Dicatat juga residual risk yang tetap berlaku di luar Group ini: assignment Owner tiket dan @mention eksplisit tetap bisa memicu notifikasi terlepas dari keanggotaan Group, jadi keduanya harus dihindari saat memakai tiket di Group ini untuk pengujian. Mitigasi #2 (penonaktifan sementara SMTP outbound saat sesi testing) belum diimplementasikan — perlu koordinasi waktu karena staging dipakai ganda (testing proyek + operasional nyata tim support).
